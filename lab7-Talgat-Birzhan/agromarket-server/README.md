# АгроМаркет API — Лабораторная 7

Выполнил: Біржан Талғат

REST API на Node.js, Express 5 и PostgreSQL для магазина АгроМаркет (продолжение лабораторной 6).
В ЛР7 добавлены пользователи, пароли-хэши (bcrypt), JWT-авторизация, роли `user` / `admin`,
ограничение попыток входа (rate limit) и защитные заголовки (helmet).

## Запуск

1. Установить PostgreSQL, создать базу `agromarket`
2. Скопировать `.env.example` в `.env` и заполнить (см. «Переменные окружения»)
3. `npm install`
4. `npm run db:init`        # создать таблицы, загрузить товары и создать администратора
5. `npm run dev`            # http://localhost:3000

## Лабораторная 7 — ответы

- **Одинаковые ли хэши у двух пользователей с одним паролем и почему:** нет, хэши разные. bcrypt добавляет к каждому паролю случайную **соль** и хранит её прямо в строке хэша (`$2b$10$<соль><хэш>`). Поэтому по базе нельзя понять, что у двух людей одинаковый пароль, и не работают заранее посчитанные таблицы «пароль → хэш». Проверку это не ломает: `bcrypt.compare` берёт соль из сохранённого хэша и хэширует с ней введённый пароль.
- **Что вернул сервер на регистрацию с `"role": "admin"`:** статус 201, но в ответе `role: "user"`. Код маршрута `/register` вообще не читает `req.body.role`, а `INSERT` не содержит столбца `role`, поэтому база подставляет `DEFAULT 'user'`. Так мы защищены от *mass assignment*; администратора создаёт только `seed.js`.
- **Почему подделанный на jwt.io токен не прошёл:** данные в JWT не зашифрованы, их можно прочитать и изменить, но подпись (`HMAC-SHA256`) считается от заголовка и данных **с секретным ключом** `JWT_SECRET`. После замены `role` на `admin` старая подпись перестаёт совпадать с содержимым, а новую без ключа посчитать нельзя. `jwt.verify` на сервере пересчитывает подпись, видит расхождение и бросает исключение, `requireAuth` отвечает 401 «Недействительный токен».
- **Что произошло после порчи токена в localStorage:** при открытии страницы React вызвал `GET /api/auth/me` с испорченным токеном; сервер вернул 401. В `apiFetch` сработала проверка `res.status === 401 && token`: токен и пользователь удаляются из localStorage, страница перезагружается, и мы снова видим форму входа как гость.
- **Почему спрятать кнопку в React недостаточно:** код React выполняется в браузере пользователя, его можно изменить или обойти (DevTools, `fetch` из консоли, Postman). Скрытая форма — только удобство интерфейса. Настоящая защита — на сервере: `requireAuth` проверяет подпись токена, `requireRole('admin')` проверяет роль, и запрос `POST /api/products` с токеном обычного пользователя получает 403, как бы он ни был отправлен.
- **401 и 403:** 401 — «я не знаю, кто вы» (нет токена, он подделан или истёк); 403 — «я знаю, кто вы, но вам сюда нельзя» (токен действителен, роль не `admin`).
- **Бонусы:** `optionalAuth` + `GET /api/orders/my` (маршрут объявлен до `/:id`), кнопка «Удалить» с `confirm()` у администратора, `PATCH /api/auth/password` (проверка старого пароля через `bcrypt.compare`, неверный старый пароль → 400, а не 401, чтобы React не разлогинил пользователя), панель заявок для администратора с выбором статуса. Выданный JWT нельзя отозвать до `exp`, поэтому после смены пароля старые токены остаются действительными до истечения срока.

## Лабораторная 6 — ответы (прошлая работа)

- **Ошибки из части 2:**
  - `price = -5` — `23514` (check_violation): сработало `CHECK (price >= 0)`;
  - без `name` — `23502` (not_null_violation): `NOT NULL`;
  - заявка с `product_id = 9999` — `23503` (foreign_key_violation): внешний ключ `REFERENCES products(id)`.
- **SQL-инъекция:** с конкатенацией строки запрос `zzz' OR 1=1 --` вернул **все** товары (условие `OR 1=1` всегда истинно, остаток запроса закомментирован); одна кавычка `'` сломала SQL — ответ 500, в терминале ошибка синтаксиса. После возврата `$1` оба адреса возвращают `[]` и статус 200: значение передаётся как данные, а не как часть SQL.
- **Двойная защита quantity:** без JS-проверки `quantity: 5` отклоняет база (`23514`, CHECK), и `errorHandler` превращает это в 400 «Значение не проходит проверку в БД»; заявка не сохраняется. JS-проверка нужна, чтобы вернуть клиенту понятное сообщение («Минимальный объём заказа — 10 кг») и не гонять заведомо плохие запросы в базу; CHECK — последний рубеж защиты, если кто-то обратится к базе в обход API.
- **Что стало с заявкой после удаления товара:** благодаря `ON DELETE SET NULL` заявка осталась, у неё `product_id = null` и `product_name = null` (`LEFT JOIN` её не теряет).
